# 22. Retry Failed Pipeline Stages (Transcript / AI / Embedding)

**Status:** ✅ Done

- **New endpoint:** `POST /api/videos/:videoId/retry/:stage` (`retryStage`) — manually retries one of the three independent side-branch stages (`transcript`, `ai`, `embedding`) after it's exhausted BullMQ's automatic 3-attempt retry and landed in a terminal `"failed"` state.
- **One handler, not three:** a `RETRY_STAGES` config map describes each stage's video-doc field, queue, job name, and precondition, so `retryStage` is a single parameterized function rather than three near-duplicate handlers.
- **Atomic reclaim:** flips `{field}.status` from `"failed"` back to `"pending"` (clearing `error`) only if it's still `"failed"` at update time, then re-adds a job to the same queue the automatic pipeline already uses — a double-click or a second open tab can't queue the job twice.
- **Precondition guard for AI/embedding:** both depend on the transcript already existing (AI needs `transcript.text`, embedding needs `transcript.segments`), so retrying either is rejected with a clear 409 unless `transcript.status === "completed"` with non-empty data — matching what the workers themselves require, so a retry never silently no-ops into `"skipped"`. Transcript itself has no precondition (only needs `objectKey`).
- **No worker changes needed:** the existing transcript/AI/embedding workers already know how to process a freshly-queued job for a video and reset status to `"processing"` on start, same as any first-time run. A successful transcript retry also auto-re-triggers AI + embedding on its own, since that's the existing first-time success path.
